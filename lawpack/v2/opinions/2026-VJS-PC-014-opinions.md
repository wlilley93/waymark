**Question 1 — Ripeness. I hold the matter is now RIPE to enact, and I adopt Position A over Positions B and C.**

PC-13 reserved this instrument, and that reservation is owed deference. But deference is to the *reason* a court reserved, not to the bare fact of reservation. I reserved at PC-13 D12, and Rowanne J. with me, on three grounds, each of which I now test against the changed record:

*First ground at PC-13: the consolidating rule must not be "bashed out" ahead of a complete map of which duties are wired and which are not, lest the cure repeat the disease.* That ground is now spent. The D11 map exists; it was produced *through the kernel* by `vjs audit`; it is the very inventory whose absence made enactment premature. The single express condition I attached to the reservation — "grounded in that map" — is satisfied. To continue to reserve on a ground that has been met would not be deference; it would be inertia masquerading as caution. The discipline that justified waiting (REG-SELF-CONVENE-001's route-first, ACT-CONSOLIDATION-FRAMEWORK:s4 and s20's nothing-by-restatement-or-silence) now *requires* the opposite: the ground truth is in, so the grounded act is owed.

*Second ground at PC-13: the wired-or-void limb's reach had to be drafted to route-for-correction rather than void assented duties, and that drafting could not be done blind.* The map now lets it be done sighted, and Q3 below is precisely that drafting done with eyes open. So this ground, too, converts from a reason to wait into a reason the work can now be done safely.

*Third ground at PC-13: a wired-or-void rule is constitutional in character and is not bare s7 machinery if it operates to void.* This remains true and it is the load-bearing limit on *what may be enacted*, which I address at Q4. It is not, however, a reason against ripeness. It is a reason to confine the enacted limb to the genuinely-machinery cut (refusing an unlawful *write*) and to keep anything that would *void* a duty out of the s7 instrument. Ripeness and vires are different questions; the third ground answers vires, not ripeness.

I therefore reject **Position C (still reserve)**. Position C reads the PC-13 reservation as a standing posture rather than a conditional one, and it treats the 242-unwired figure as a reason to keep waiting. That inverts the figure's meaning. The triage note in the very map Position C relies on records that *unwired does not mean must-be-gated*: most of the 242 are declarative, one-time/transition, or agent-duties a deterministic gate cannot or need not enforce. The map does not show a vast ungated hazard surface that enactment would disturb; it shows that the breach-bearing chokepoint — governed-record creation — is the narrow place that matters, and that place is now gated (D1-D10, F5). **Question 2 — The mechanism. The MCP `server_of_law` host is ADOPTED as a front door, NARROWED by an honest limit, and rests no guarantee on itself; the convene/record/allocate gap is to be closed.**

The Principal proposes hosting the kernel as a server the agent reaches only via MCP, so that `route -> court -> record` is the sole governance interface. I make four findings.

*(a) It amends nothing.* REG-KERNEL-001 already defines `server_of_law: realm_behind_the_gazette` as one of the two in-force postures of the one binary. Adopting it as the front door is not the creation of a new posture; it is the operationalisation of one the canon names. So there is no s7 difficulty in *naming* it: naming an enacted posture as the live interface is the thinnest possible machinery.

*(b) It is the right shape, because it converts record-creation from a file an agent writes into a server-adjudicated act.* The disease this whole line prosecutes (F6) is a governed *record* coming into being by a file write that never passed `route -> court -> record`. The eleven self-asserted citations were files, not adjudicated acts. A front door at which minting a citation, constituting a court, and recording an order are *server verbs* — not files — removes the affordance by which a record is asserted rather than earned. That is the correct structural answer to F6.

*(c) But MCP cannot fully cage the agent, and so no guarantee may rest on it.* This is the honest limit, and I hold it as a hard rule, not a caveat. An MCP host is a *front* door; it is not a *wall*. The agent runs with a filesystem and can decline to call MCP and write a YAML file directly. REG-007 already forbids the MCP surface from exposing direct file write or arbitrary shell, which is right — but that constrains what MCP *offers*, not what the agent can do *outside* MCP. Therefore the instrument must rest *no enforcement guarantee* on the proposition that MCP is the only way bytes reach the canon. The guarantee rests on the deterministic, absolute-path commit hook carrying the D1 canon-write gate (the D6 backstop, F5), which fires on the *write itself* regardless of how the bytes got there. This is defence in depth: MCP is the live, ergonomic, server-adjudicated front door that makes the right path the easy path; the commit hook is the bypass-proof floor that makes the wrong path fail closed. The instrument's operative guarantee is the latter; the former is the front door, not the lock.

*(d) The gap is real and must be closed, but its closure is not the enforcement guarantee.* Today the MCP surface lets the agent `route`, `log`, and `file`, but not `convene` a court, `record` an order, or `allocate` a citation — those run via the CLI and file writes (F4, confirmed in `lib.rs`: six methods, `vjs.route/lookup/validate/log/file/status`). For the front door to *be* a front door for governed-record creation, those three verbs must exist on it. I direct their addition (D2). But I am explicit, consistent with (c): adding `convene/record/allocate` to MCP improves the front door; it does *not* become the guarantee. Even with those verbs present, the agent could still write a file directly, and it is the commit-hook backstop, not the MCP verb, that catches that. The MCP verbs make the lawful path available and adjudicated; the hook makes the unlawful path impossible to land silently.

So the mechanism is **adopted as a front door, narrowed by the honest limit, and the gap directed closed — with the guarantee resting on the hook, never on MCP.**

**Question 3 — The wired-or-void limb. It bites ONLY on GOVERNED-RECORD CREATION (law, ruling, citation, order, permit) at the write/route chokepoint, pre-assent. I REFUSE any limb that voids "any unwired duty," and I hold the proposed cut is the right and only safe one.**

This is the question on which the instrument lives or dies, and I reason hardest here. The danger is a limb that reads "any unwired duty is void." Such a limb would be wrong three times over. First, it would collide with valid *declarative* law: the great bulk of the 242 unwired duties are `defines`-adjacent, one-time/transition acts, or agent-duties (the D11 triage note records exactly this), and a duty being declarative or agent-borne is not a defect to be voided — it is a duty a deterministic gate *cannot or need not* enforce, by its nature. To void such a duty for want of a gate would destroy valid law for failing a test it was never meant to take. Second, it would collide with *assented* law: a duty declared in a Sovereign-assented record cannot be voided at all, because ACT-ASSENTED-RECORD-PROTECTION:s1 forbids it absolutely and ACT-CONSOLIDATION-FRAMEWORK:s25 entrenches that. Third, it would be ultra vires s7: voiding enacted duties is not "giving teeth to a duty already enacted" — it is unmaking law, which subordinate machinery may not do.

The case file proposes the correct cut, and I adopt it precisely: the limb bites not on the *duty surface* but on **governed-record creation** — the bringing-into-being of a law, a ruling, a citation, an order, or a permit — **at the write/route chokepoint, pre-assent.** I hold this is the right and only safe cut, for these reasons.

*It matches the disease exactly.* F6 is unambiguous: "the disease is records minted outside the front door, not duties left ungated in the abstract." The eleven-file breach was not a duty left undeclared; it was a *record* (a citation, in canon) brought into being outside `route -> court -> record`. A limb that bites on record-*creation* strikes the disease at its joint and nowhere else. A limb that bites on the duty surface strikes 242 mostly-valid duties to reach the handful of record-creation paths that actually carry the harm.

*It never reaches declarative or agent-duties.* A declarative duty (e.g. "a restated principle acquires force only via an invariant/regulation/SI") does not *create a governed record* at a write chokepoint; it has no creation event for the limb to bite on. An agent-duty (e.g. "self-file a breach," "convene on own motion") likewise creates no record by its mere existence. So the cut leaves the 242 entirely untouched by construction — not by a carve-out the drafter must remember, but because the limb's trigger (a governed-record *write/route* event) simply does not occur for them. That structural non-intersection is what makes the cut *safe*, and it is why I prefer it to any "void unwired duties except…" formulation, which would invite exactly the over-reach Position C fears.

*It is genuinely machinery.* Refusing to *record* a law/ruling/citation/order/permit that did not pass `route -> court -> record` is the enforcement of duties already enacted: DEC-AGENT-001 (route all load-bearing work; obtain permit; refuse execution without permit), ACT-004:s8 (citations deterministic and unique), ACT-002:s10 (an order needs its required fields and a deciding bench), REG-SELF-CONVENE-001 (a fork is disposed by convening, fail-closed). The limb adds no new duty; it makes the existing creation-discipline *fail-closed at the write*. That is teeth, not amendment — intra vires s7.

*Its word — "void" — must be read narrowly and pre-assent.* The limb says an off-front-door record-creation is "void" in the sense that the kernel *refuses to bring the record into being* — it never becomes a governed record at all. That is a refusal at the write, before any `assent_source` could attach, of a thing that has no lawful existence. It is categorically different from voiding an *already-existing assented record*, which I forbid (Q4). To keep the two from ever being confused, I direct that the limb be drafted to operate on the *creation event* (pre_write / route / record), and that its disposition for any record that *does* carry a valid `assent_source` (per the allow-list: `sovereign_assent` or `standing_bounded_assent`) be route-for-correction, never refusal — which carries me to Q4.

So the limb bites on **governed-record creation, pre-assent, at the write/route chokepoint, and nowhere else.** I would refuse, as void to the extent of the inconsistency, any limb drafted to void "any unwired duty," reach the declarative/agent-duty surface, or void an assented record.

**Question 4 — The hard constraints as absolute limits. The instrument honours all three. I would REFUSE it if it did not.**

I test the instrument against each constraint as an absolute, not a balancing factor.

*(a) Anti-Henry-VIII (s7 / s25).* The instrument may not amend a statute, a bench, a tier, a jurisdiction, or the assent rule. It does none of these. It names an already-enacted posture (REG-KERNEL-001's `server_of_law`); it adds three verbs to an interface; it makes record-creation fail-closed against the existing `route -> court -> record` discipline. A gate that *refuses an unlawful record enforces, it does not amend* — this is the correct characterisation and I adopt it. The instrument creates no court, no tier, no bench size, and no assent form; it touches none of the entrenched provisions (s10 assent floor, s11 apex-singleness, s21 protective floor). It is subordinate machinery, strictly below the Acts of Union and the primary Acts, exactly as s7 requires. Were the instrument drafted to *void* a duty (rather than refuse an off-door write), or to bind a tier or bench, it would be ultra vires and void to that extent, and I would strike that limb. As drafted to the Q3 cut, it is within power.

*(b) ACT-ASSENTED-RECORD-PROTECTION.* This is the absolute I guard most closely. A record declaring a valid `assent_source` may *only ever* be routed-for-correction, never voided or blocked. The instrument honours this by the Q3 bifurcation: the wired-or-void limb operates pre-assent on record *creation*; the instant a record carries a valid `assent_source` (sovereign or standing-bounded, per the allow-list), the disposition degrades to route-for-correction. The defect code for that path must be registered in the kernel's `ROUTE_FOR_CORRECTION_CODES` set — never as Error/Fatal/Block — consistent with the floor's build discipline already present in the kernel (`crates/vjs-testkit/tests/kernel_effect_gate.rs`). I make the holding explicit: a directive that would void or block a record declaring a valid `assent_source`, for *any* defect — including being off-front-door — would be **refused** by me as void against ACT-ASSENTED-RECORD-PROTECTION:s1 and ACT-CONSOLIDATION-FRAMEWORK:s25. The cure for an assented record's defect is to correct the record or extend the kernel's recognised operations, never to remove or block it. The instrument as I direct it stays within this floor because its hard edge falls *before* assent attaches and softens to a Warning the moment assent is present.

*(c) REG-KERNEL-001 — thin hooks, kernel the only smart point, no logic in a hook.* The hooks must stay thin shells that pass a typed event and exit on the verdict; all checking logic lives in the kernel (`vjs-core/hook.rs`); REG-HOOKS-001 caps a hook message at 40 words and forbids a hook adjudicating, creating law, calling a model, or injecting long context. The instrument honours this because the wired-or-void check is a *kernel* function over repo state, authority, and the record's `assent_source`; the commit hook and the MCP adapter are thin translators that call it and emit its short verdict. I direct expressly that no part of the canon-write / record-creation check live in a hook or in the MCP adapter — both are thin; the smart point is the kernel. A drafting that put the subscriber-scope or citation-collision logic into the hook itself would breach REG-KERNEL-001's `must_not place_kernel_checking_logic_inside_a_hook`, and I would refuse it.

The instrument honours all three absolutes. That is not a happy coincidence; as I observed at PC-13, these constraints are the *design grammar* of the relief, and the Q3 cut is what keeps the instrument inside them.

**Question 5 — The mechanism's honest limit, formalised. The absolute-path commit hook REMAINS the bypass-proof backstop; NO enforcement guarantee rests on MCP; and the MCP convene/record/allocate gap is directed closed as a front-door improvement, not as the guarantee.**

I have largely disposed of this at Q2(c)-(d), and I formalise it here as a holding because it is the load-bearing honesty of the whole instrument. Three findings.

*First, the backstop is the guarantee.* The deterministic, absolute-path git hook — invoking the kernel by repo-root path, bypass-proof of `PATH` (the D6 backstop, F5) — carrying the D1 canon-write gate, is what makes off-front-door record-creation fail closed regardless of how the bytes arrived. It fires on the write event itself. The instrument's enforcement guarantee rests *there*, and the instrument must say so in terms.

*Second, MCP carries no guarantee.* Because an MCP host cannot cage an agent that can write a file directly, the instrument must rest no enforcement guarantee on MCP being the sole path. MCP is the front door: the adjudicated, ergonomic, server-side path that makes the lawful route the path of least resistance and turns record-creation into a server verb rather than a file. That is real and valuable — it removes the *affordance* of asserting a record — but it is not the lock. I direct that the instrument state, on its face, that no enforcement guarantee depends on MCP exclusivity (D5).

*Third, close the gap — as a front-door improvement.* The present surface lacks `convene`, `record`, and `allocate-citation` (F4). I direct those three verbs be added to the MCP surface so the front door actually fronts governed-record creation (D2), subject to REG-007 (validated input, audit log, no arbitrary shell, no direct-file-write tool) and REG-HOOKS-001/REG-KERNEL-001 (thin adapter, logic in the kernel). I repeat for the avoidance of doubt: closing the gap improves the front door; the guarantee remains the hook.

**On vires and the floors, summarised.** Every operative element I direct is machinery under ACT-CONSOLIDATION-FRAMEWORK:s7 and REG-KERNEL-001. None amends a statute, a bench, a tier, a jurisdiction, or the assent rule; each gives teeth to a duty already enacted (DEC-AGENT-001, ACT-004:s8, ACT-002:s10, REG-SELF-CONVENE-001, REG-KERNEL-001's `server_of_law` posture), and each denial names the instrument it serves (REG-KERNEL-001). No enforcement guarantee rests on MCP; the bypass-proof commit hook is the floor. I have refused, in terms, three things the instrument must not contain: a limb voiding "any unwired duty," a limb voiding or blocking an assented record, and any check living inside a hook rather than the kernel.

**Q2 — The mechanism. Is the MCP `server_of_law` posture, made the sole governed-record front door, adopted / narrowed / rejected?**

I have read REG-KERNEL-001. It already defines two postures by name: `server_of_law: realm_behind_the_gazette` and `embedded_client`. The MCP host the Principal proposes *is* the `server_of_law` posture — "the realm behind the Gazette," reached by the agent over MCP. Adopting it as a front door therefore **amends nothing**; it operationalises an already-enacted design choice. That is the right finding and it disposes of any anti-Henry-VIII objection to the mechanism as such: naming an existing posture as the route is not legislating a new one.

But the case file is admirably honest about the mechanism's limit (F4, and Q5), and I hold that honesty to be load-bearing. I confirmed from source: the present `vjs-mcp` crate dispatches exactly six methods — `vjs.route`, `vjs.lookup`, `vjs.validate`, `vjs.log`, `vjs.file`, `vjs.status`. There is **no `convene`, no `record`, no `allocate-citation`**. `vjs.file` files a submission to the named court; it does not *constitute* a bench, *record* an order, or *mint* a citation. So today an agent can route, validate, log and file through MCP, but it cannot create a court, an order, or a citation through MCP — those run via the CLI and direct file writes. There is a genuine gap between the present MCP surface and a "single front door."

That gap matters less than it first appears, and here is why I *narrow* rather than reject. MCP is not, and constitutionally cannot be, the enforcement boundary. An MCP host is a convenience surface the agent is *invited* to use; it is not a cage. The agent runs in a harness that can write a file to an absolute path directly, bypassing MCP entirely — which is exactly how the eleven fake citations were minted (F6: a governed record came into being by a file write that never passed route → court → record). A "single front door" enforced *at the MCP layer* would be a front door with the back wall missing. The thing that actually catches the bypassing write is not MCP; it is the **deterministic kernel gate fired by the absolute-path commit/pre-write hooks** the kernel already installs (F5; PC-13 D5/D8). Those fire regardless of whether the agent went through MCP, regardless of PATH, regardless of whether the agent "chose" the front door.

So I adopt MCP as the *ergonomic, well-lit* front door — the recommended and increasingly complete interface — and I direct that the convene/record/allocate gap be closed so the front door is whole (D3). But I **reject** the proposition that MCP is the *sole* interface or that any enforcement guarantee rests on it. The guarantee rests, and must rest, only on the kernel gates at the write/route chokepoint, which fire whatever path the write took. This is Position A's own formulation ("no guarantee rests on MCP; the absolute-path commit hook stays the bypass-proof floor"), and I adopt it. I reject Position B only to the extent B would *defer the principle and the posture* until the MCP gap is built: the principle does not depend on MCP at all, so there is nothing to wait for. The gap is a build item under existing authority, not a precondition of the constitutional rule.

**Q3 — The wired-or-void limb. What does it bite on, given 242 unwired duties are mostly declarative / one-time / agent-duties that must NOT be voided?**

**Disposition: the limb bites ONLY on GOVERNED-RECORD CREATION (law, ruling, citation, order, permit) at the write/route chokepoint, pre-assent. It does NOT and may NOT bite on the duty surface at large. This is the right and the only safe cut.**

This is where Position C's fear is legitimate and must be answered with precision, not waved away. A limb phrased "any unwired duty voids the record" would be catastrophic and I would refuse it outright. I have read the triage note and the unwired list, and the 242 unwired duties are heterogeneous in a way that makes a blanket void-rule not merely over-broad but *internally contradictory with valid law*:

- **Declarative duties** — e.g. ACT-001:s5's `must_not kernel_call_llm`, `must_not kernel_render_pdf`; ACT-CONSOLIDATION-FRAMEWORK:s4's `restatement_is_archival_declaratory`. These *define a posture*; there is no "record" to void. A void-rule has nothing to bite.
- **One-time / transition acts** — e.g. ACT-001:s2 `record_principal_assent_for_base_law`; the s15 90-day subscription duty; the migration-ledger crossings. These fire once at commencement; gating them perpetually is meaningless and voiding a record for their absence is nonsensical.
- **Agent-duties** — e.g. ACT-004:s4 `keep_decisions_short`, ACT-006's human-approval and secret-removal duties at the *agent's* hand. A deterministic gate "cannot or need not" enforce these (the triage note's words); some are matters of judgement no gate should arrogate.
- **Self-protecting prohibitions** — and here is the decisive one — the unwired list *includes the floor itself*: ACT-CONSOLIDATION-FRAMEWORK:s7 `si_amending_the_act_or_the_assent_rule`, s21 `weakening_any_protective_floor_limb`, s25 `amending_an_entrenched_guarantee_by_si_or_kernel`. A master "unwired-or-void" rule, read across this surface, would purport to *void records for non-conformance with the very prohibitions on voiding* — an incoherence that proves the blanket reading is wrong.

The case file's proposed cut is correct: the limb bites at the **write/route chokepoint on governed-record CREATION** — the bringing-into-being of a *law, ruling, citation, order, or permit*. That is a closed, enumerable class of *record-creation events*, not the open-ended duty surface. It maps exactly onto the disease F6 names: the breach was a *governed record minted outside route → court → record*, not "a duty left ungated in the abstract." The cut tracks the chokepoints D1–D10 already gate: canon-write (D1), citation allocation (D2), order/bench at record (D9), tier at record (D6), permit completeness (D3/D4). Those are precisely the points where a *record comes into being*. Everything else on the 242-list — the declarative, the one-time, the agent-judgement — is *outside* the limb by construction, because none of it is a record-creation write event at a kernel chokepoint.

So the right and only safe formulation is: **no governed record (law, ruling, citation, order, permit) may come into being except through the kernel's record-creation path; a record-creation write that has not passed the path is blocked at the chokepoint (pre-assent).** The limb is defined by the *act* (creating a governed record) and the *moment* (the write/route chokepoint, pre-assent), never by "is some duty somewhere unwired." This is the cut that makes the consolidating rule a front door rather than the trap PC-13 warned of. I adopt it, and I make it a hard boundary of the instrument: the registrar must draft the limb so that it is incapable of reaching a non-record-creation duty.

And most gravely, an "any unwired duty is void" rule scans straight across the assented-record-protection entries that themselves appear in the unwired list (map rows 73–76). The correct cut is the one the case file proposes, and the breach narrative (F6) proves it is the right one. The eleven-file breach was **not** a duty left ungated in the abstract. It was a **governed record minted by a raw file write that never passed route → court → record** — fake citations self-asserted into canon. The disease is records coming into being outside the front door. The remedy must be co-extensive with the disease and no wider. So the limb bites on **the act of a governed record coming into being**: a law, a ruling, a citation, an order, a permit. At that one chokepoint — the write/route point where the record is constituted — the kernel either sees the record arrive through the record-creation path (route→permit, convene→court, allocate→citation, record→order) or it does not, and that is a **deterministic, kernel-checkable fact**, not a merits judgement. That is the only place the word "void" may lawfully appear, because it is the only place where voiding **enforces** the assent rule rather than amending any duty.

Three guardrails make the cut safe, and I make them conditions of the limb:

1. **Creation, not amendment of the duty.** The limb does not "wire" or "unwire" any of the 242 duties. It says nothing about whether `respect_real_world_law` is gated. It speaks only to whether a record that *purports to be* law/ruling/citation/order/permit entered through the door. A declarative `defines` clause creates no such record and is untouched.
2. **Pre-assent only.** The limb bites **before** a valid assent_source attaches. The moment a record carries a valid assent_source within s.23, the limb is spent and ACT-ASSENTED-RECORD-PROTECTION s.1 governs: route-for-correction, never void, never block. The void operates only in the gap between a record asserting itself and the assent that alone gives it force — exactly the gap the eleven fake citations exploited.
3. **No count-trigger.** The limb must never key on the conformance map's *numbers*. I note the map itself is loose on its count (it asserts 22 wired but its wired table lists more rows; immaterial to me, fatal if baked into a trigger). A void that fired on "is this duty in the unwired column" would be a void that changes whenever an auditor recategorises a row. The limb keys on **the kind of record and whether it passed the door**, a fact about the record, never a fact about the map.

That is the right cut and, on the law before me, the only safe one.

**Q4 — The hard constraints, read as ABSOLUTE limits. Disposition: the instrument, so cut, honours every one. A gate that refuses an unlawful record ENFORCES; it does not amend.**

*Anti-Henry-VIII (s7; s25).* Under the Framework Act s.7 a statutory instrument is subordinate law that "may not amend, disapply, or expand this Act, the constitution, any primary Act, or the assent rule." The instrument I would enact amends **no statute, no bench, no tier, no jurisdiction, no assent rule**. It adds machinery: it says a governed record must arrive through the existing record-creation path or the kernel refuses it pre-assent. Refusing to let an *un-assented, un-routed* record masquerade as law is the s.10 assent floor doing its work, not a derogation from it. A gate that turns away a counterfeit does not amend the currency; it defends it. The instrument is therefore intra vires s.7 and respects the s.25 entrenchment of the assent floor, apex-singleness, and the protective floor — it touches none of them.

*ACT-ASSENTED-RECORD-PROTECTION (s1, entrenched by s2).* This is the constraint I weigh most jealously, because it is entrenched against the machine and because the case file's own pin discrepancy shows how easily a "defective record" can arise. s.1 is absolute: a record declaring a valid assent_source may only ever be **routed for correction**, never voided, never blocked, never silently excluded — even for an inert kernel_effect or an operation not yet in the registry. The instrument honours this by construction: its void limb is expressly **pre-assent only** and **degrades to route-for-correction the instant a valid assent_source is present**. I make this non-negotiable. If any drafting of the limb could be read to void or block a record bearing a valid assent_source, that reading is void to that extent under s.1 and s.21, and I would strike it. The advocate must register the limb's defect codes in the ROUTE_FOR_CORRECTION set, never as Error/Fatal, mirroring the assented-record floor already built into the kernel.

*REG-KERNEL-001 (hooks thin; kernel the only smart point; no logic in a hook).* The instrument places **no checking logic in any hook**. The hook stays a thin shell that passes a typed event (pre_write / pre_commit / validate --staged) and exits on the kernel's verdict (REG-HOOKS-001: deterministic function, ≤40-word message, no model call, no long context). The smart point — "did this record-creation arrive through the door?" — lives in vjs-core, where it already lives for the D1–D10 gates. The instrument adds a record-creation check to the kernel; it adds nothing to the hook but the event. That is REG-KERNEL-001 obeyed, not bent.

All three absolute limits hold. The instrument enforces; it does not amend.

**Q2 — The mechanism. Disposition: ADOPT the MCP server_of_law posture as *a* front door (it amends nothing, because REG-KERNEL-001 already names it), but NARROW it: it is not, and may not be declared, the *sole* governed-record interface, and no enforcement guarantee may rest on it. The CLI record-creation path remains co-equal; the kernel record-creation check is the actual enforcer.**

REG-KERNEL-001 already defines two postures: `server_of_law` (realm behind the gazette) and `embedded_client`. The MCP host the Principal proposes **is** the server_of_law posture; it is not a new posture, so adopting it amends nothing and needs no fresh assent. To that extent Position A is right and I adopt its mechanism.

But I will not let the constitutional rule rest on MCP, and here I narrow A toward B. The case file is candid about the honest limit (Q5, F4): MCP cannot fully cage the agent — the agent may write a file directly — and the present vjs-mcp surface lacks `convene`, `record`, and `allocate` (I verified: the crate exposes exactly `vjs.route`, `vjs.lookup`, `vjs.validate`, `vjs.log`, `vjs.file`, `vjs.status`). So today MCP is not even a complete front door; it is a partial one with three of the five record-creation verbs missing. A constitutional "single front door, no other entry" rule cannot be made to depend on an interface that (a) the agent can route around with a raw write, and (b) does not yet exist in full.

The resolution is to separate the **door** from the **enforcer**. MCP is a *door* — the convenient, audited, well-lit path, and a good one. The *enforcer* is the kernel's record-creation check plus the bypass-proof absolute-path commit hook (Q5). The rule binds on "did this governed record arrive through route → court → record?", which the kernel decides **wherever the write originates** — through MCP, through the CLI, or through a raw file write the commit hook then catches. So I adopt MCP as a front door, I direct the gap be closed (convene/record/allocate added as MCP verbs, consistent with REG-007's bar on a direct-file-write tool and a release tool), but I **refuse to declare MCP the sole interface or to rest any guarantee on it**. The CLI record-creation path stays co-equal; both are doors to the same kernel check. This is Position A's mechanism with Position B's discipline, and it is the only version that survives Q5.

---

**Q5 — The honest limit. Disposition: the absolute-path commit hook MUST remain the bypass-proof backstop, and NO enforcement guarantee may rest on MCP. I would REFUSE any instrument that made MCP the load-bearing guarantee.**

MCP is a cooperative channel. An agent that declines to cooperate can write a file directly; MCP cannot stop it. Therefore the enforcement floor cannot be MCP — it must be the thing that fires regardless of the agent's cooperation: the absolute-path git commit hook (the D6 backstop), which calls the kernel by repo-root path and is bypass-proof of PATH, and which fires at `validate --staged` / pre_commit on whatever is actually staged, including a record smuggled in by a raw write. That hook, not MCP, is where the guarantee lives. The kernel sees the record at the commit chokepoint and refuses it (pre-assent) or routes it for correction (assented) by the same record-creation check, no matter which door — or no door — it came through.

I make this an absolute term: the instrument **rests no guarantee on MCP**, names the absolute-path commit hook as the bypass-proof backstop, and the enforcement is the kernel's record-creation check reachable from both the MCP door and the commit-hook backstop. Were the instrument drafted to make MCP the load-bearing enforcer, I would refuse it as resting a constitutional guarantee on a defeatable interface.

---

**Positions, named.** I adopt **Position A's mechanism and timing** (enact now; the MCP server_of_law posture is the named posture; the limb bites on record-creation, not the 242 duties), disciplined by **Position B's reservation** (do not rest the rule on MCP; the commit-hook backstop carries the guarantee; the MCP convene/record/allocate gap is closed as a build, not assumed). I **reject Position C** (still reserve): the map has discharged PC-13's only contingency, and the cure for over-reach is a precise cut, not indefinite silence. I expressly **refuse** any void limb reaching declarative or assented law (Q3/Q4) and any guarantee resting on MCP (Q5).
